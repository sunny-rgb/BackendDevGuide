## 2026.02.24

### 问题1.

> 【MiniMax 一面】讲一下 RAG 的全流程？从用户输入到最终输出经历了哪些步骤 

**RAG**就是检索、增强、生成。

首先基于现有知识库文档（pdf、doc、md、html等），进行文本读取和切分，常用的切分策略包括**基于分隔符**、**基于语义相似度**和**父子分块索引**等，最长用的是**递归父子分块结合滑动窗口算法**实现针对语义的精准切分。调用Embedding模型对chunk块进行向量化，同时将chunk过程中自定义组织好的元数据等信息存入**elastic**或**milvus**向量数据库，辅助后续索引。

用户输入一个文本问题后，先进行**查询预处理**，清洗掉空格、特殊字符、错别字等，结合上下文补全指代，改写查询。同样进行**query embedding**，采用和知识库相同的向量模型，将这个问题向量化。

接着和向量数据库进行检索，检索的主要原理是根据**相似度计算**，常用的有**余弦相似度**、**点积**、**欧式距离**，返回前**Top-K**个文本片段。通常采用**多路召回的混合检索**策略：**向量检索** + **BM25关键词检索** + metadata标签元数据辅助。

召回后处理，去掉重复片段，重新排列并过滤掉低相关片段，将这些新拼接好的文本片段和问题作为llm的prompt，交给大模型生成。

大模型基于知识库和问题，返回最终生成的答案。



### 问题2.

> 检索是怎么检索的？怎么把文档通过 Embedding 做成向量的？文档和嵌入向量的区别是什么？

检索首先将知识库和问题embedding为高维向量，通过余弦相似度、欧式距离等计算，返回前Top-k个片段，检索时可以混合chunk过程中的metadata。

文档是文本内容，包括pdf、doc、md、html等；**嵌入向量**是上述文本内容在高维向量空间的映射，可以更加方便的计算相似度，并且维度是固定的。

> 相似度如何计算？常用的相似度计算方法？哪种效果最好？

| **度量方式**   | **关注点** | **范围**             | **归一化** | **计算复杂度** | **最佳应用** | **例子**   |
| -------------- | ---------- | -------------------- | ---------- | -------------- | ------------ | ---------- |
| **余弦相似度** | 方向/角度  | $[-1, 1]$            | ✅ 自动     | $O(n)$         | 文本/语义    | 文档相似度 |
| **欧氏距离L2** | 绝对位置   | $[0, +\infty)$       | ❌ 需要     | $O(n)$         | 图像/坐标    | 人脸识别   |
| **内积**       | 方向+大小  | $(-\infty, +\infty)$ | ❌ 需要     | $O(n)$ 最快    | 推荐/排序    | 商品推荐   |

余弦相似度常用于高维空间，因为它只在乎向量的“夹角”，而不受向量绝对长度的影响。



>KNN和ANN算法？

**KNN** 和 **ANN **对比

| **特性**         | **KNN (K-Nearest Neighbors) - 精确搜索** | **ANN (Approximate NN) - 近似搜索**            |
| ---------------- | ---------------------------------------- | ---------------------------------------------- |
| **搜索方式**     | 暴力搜索，遍历所有数据点                 | 索引优化，跳过大部分数据                       |
| **时间复杂度**   | $O(n \cdot d)$                           | $O(\log n)$                                    |
| **准确率**       | 100%                                     | 95-99%                                         |
| **10亿数据耗时** | 10秒+                                    | 约 100ms                                       |
| **核心思想**     | 扫描所有点                               | **通过预建索引，将搜索空间划分，避免全量扫描** |

主流ANN算法

- **HNSW** (分层导航小世界)，基于多层导航图
  - 结构： 多层图结构。
  - 原理： 从顶层快速定位，逐层精细搜索。
  - 优点： 速度快，精度高。
  - 应用： Milvus 默认选择。

- **IVF** (倒排文件索引)
  - 原理： 基于 K-means 聚类，先找最近簇心，再搜索簇内向量。
  - 优点： 内存效率高。
  - 场景： 适合大规模数据。

- **LSH** (局部敏感哈希)
  - 原理： 随机投影哈希，使相似向量同桶；通过多哈希表增强。
  - 特性： 有理论保证。
  - 场景： 适合高维稀疏数据。

在 RAG 里发生的是：

```
1️⃣ Query → embedding
2️⃣ ANN 索引结构筛选候选向量
3️⃣ 对候选向量计算真实距离（余弦 / L2）
4️⃣ 选 TopK
```

所以更准确地说是：

ANN 负责“缩小搜索范围”，余弦相似度负责“最终排序”。

> 混合检索架构？

**混合搜索技术 (Hybrid Search)**

定义：向量语义 + 关键词匹配 + 元数据过滤的完美融合，也就是V + K + M，旨在取长补短。

| **方式**       | **核心机制**             | **优势**                   | **不足**                           |
| -------------- | ------------------------ | -------------------------- | ---------------------------------- |
| **向量搜索**   | 语义空间相似度计算       | 理解语义相似性、处理同义词 | 易漏掉精确匹配词、对专有名词不敏感 |
| **关键词搜索** | **BM25**/TF-IDF 精确匹配 | 匹配能力强、对专有名词敏感 | 缺乏语义理解、受词义鸿沟影响       |
| **元数据过滤** | 结构化属性筛选           | 精准筛选范围（时间、类别） | 限制过死可能导致无结果             |

混合搜索架构与融合策略

查询流程：用户查询 ➔ 查询解析 ➔ (并行) 向量搜索 + 关键词检索 + 元数据过滤 ➔ 融合策略 ➔ 最终结果。

主流融合策略 (Fusion Strategies)：

- **RRF (Reciprocal Rank Fusion)**：简单有效，对异常值鲁棒，无需分数归一化。
- **线性组合 (Linear Combination)**：基于权重 score=α⋅vector+β⋅keyword，灵活性高。
- **Cross-encoder 重排序**：先召回再精排，精度最高但计算成本较大。
- **Learning to Rank (LTR)**：基于点击率、停留时间等特征持续学习，效果最优。

### 问题1. 

> 【字节跳动一面】RAG 用户提问和向量库中的语义发生不匹配怎么办？如何解决语义鸿沟问题？

**语义鸿沟**：本质是用户提问的问题，和知识库中已有的文档存在不一致。

**核心问题**：用户查询往往模糊、简短，存在词汇鸿沟，直接检索效果差。常见的有：

- 表达差异：

  - 用户问：“怎么避免缓存击穿？”
  - 文档写的是：“防止热点 key 失效导致数据库压力过大”

  👉 表达不同但语义相同

- 术语不一致：

  - 用户说：“大模型微调”
  - 文档写的是：“参数高效调优（PEFT）”

- 颗粒度不匹配：

  - 用户问宏观问题
  - 文档是细节片段

- Embedding 能力不够

  - 用的 embedding 模型语义理解弱
  - 向量维度太低
  - 领域不匹配

常用的办法有：

- 方案 1：**查询重写（Query Rewrite）**，也可以叫**子查询扩展**

  这是最有效的方法。在向量检索前：用户原始问题 → LLM改写 → 多个等价问题 → 检索

  例如：用户问：怎么避免缓存击穿？

  改写成：如何防止热点 key 失效如何解决缓存失效导致数据库压力过大缓存击穿的解决方案有哪些。

  然后**多路检索（Multi-Query Retrieval）**。召回率从 65% 提升至 85%，有效覆盖更多相关文档并减少词汇鸿沟。查询重写又包括**单轮查询重写**和**多轮对话查询重写**。

- 方案2：**HyDE (假设性文档嵌入)**

  核心原理：LLM 基于查询生成“虚假”的假设答案文档。对假设文档进行向量编码。用**文档-文档相似度**进行检索（比**查询-文档**更准确）。优势：在零样本场景下效果显著，特别适合复杂技术文档检索，NDCG@10 提升 15-20%

- 方案 3：**多路召回的混合检索（Hybrid Search）**

  不要只用向量检索。结合：**语义向量相似度**和**BM25关键词检索**

  例如：score = α * semantic_score + β * keyword_score

  避免纯语义偏移，保证关键词命中，大多数工业级RAG都这样做。

- 方案 4：**改进 Chunk 策略**

  很多语义鸿沟来自：切分太碎。如果 chunk 太短：语义不完整，向量表达弱

  建议：300～800 tokens；保持语义完整；使用滑动窗口

- 方案 5：使用**更强的 Embedding 模型**

  如果你用的是小 embedding 模型：换成：更高维模型；领域专用 embedding；instruction-tuned embedding。Embedding 模型的质量决定上限。

- 方案 6：增加 **Metadata 过滤**

  例如：文档类别、主题标签时间范围先过滤，再向量搜索。

- 方案 7：**Re-rank（二阶段重排）**

  向量检索 Top50→ Cross-Encoder Re-ranker→ 选 Top5。Re-ranker 能大幅减少语义误匹配。
  
  

### 问题2. 

> 【快手AI应用一面】上下文场景中，单Agent和多Agent各自的优劣势是什么？什么情况下选择单Agent，什么情况下选择多Agent？

Agent  = LLM + Prompt + Memory + Tool + Planning能力

本质差异是：是让一个模型承担所有角色，还是把任务拆成多个专门角色？

**单Agent**的优劣势

- 优势
  - 架构简单，好维护，不需要Agent通信机制，不需要调度器
  - 延迟低，少一次模型调用，少多轮交互
  - 上下文天然一致
  - 不存在跨Agent信息丢失
  - 没有状态同步问题
- 劣势
  - Prompt会越来越复杂：当任务变多：你是面试官 + 评分官 + 出题人 + 反馈专家 + 数据分析师，Prompt会非常长。
  - 容易角色混淆，逻辑容易乱，输出风格不稳定
  -  可扩展性差，加功能只能继续堆prompt。

**多Agent**的优劣势

- 优势
  - 专业化分工（最核心优势）。例如：Agent A：出题，Agent B：追问，Agent C：评分，Agent D：反馈每个Agent prompt都可以非常干净。
  - 更容易扩展加新功能：新增一个Agent，不用改原有逻辑。
  - 更适合复杂流程：比如：需要规划，需要多轮推理，需要工具调用，需要RAG多阶段处理。
  - 更接近真实组织结构：比如模拟面试：技术面试官，HR复试官
- 劣势
  - 架构复杂度飙升 ：需要Agent通信机制，状态管理，调度系统，错误恢复机制
  - 成本高：多次模型调用，Token消耗多
  - 调试困难：我们要排查：是哪个Agent出错？是调度逻辑问题？还是提示词问题？
- 什么时候用单Agent？适用场景
  - 任务逻辑线性：比如普通问答，简单RAG，工具调用很少
  - 功能少于3个核心职责：比如：查询 → 总结 → 输出
  - 产品早期：快速验证，先跑通闭环，不考虑扩展性
- 什么时候必须用多Agent？
  - 明确存在角色分离：例如：规划者（Planner）执行者（Executor），审核者（Critic）
  - 任务是非线性的：例如：需要反思，需要重试，需要分支决策
  - 任务复杂度高：比如：代码生成 + 运行 + 调试，RAG多阶段自动报告生成
  - 需要长期记忆管理：不同Agent管理不同Memory。
- 结合现在的模拟面试系统Go + Eino + 多智能体模拟面试。我建议结构：不要一开始就全拆。推荐路线：先单Agent，再拆成多Agent这是工业界主流做法。也就是**渐进式多Agent**。

### 问题1.

> 【百度一面】MCP 的好处？MCP 和 Function Call 区别？

**MCP（Model Context Protocol）**，它是一种标准化的大模型工具接入协议。

可以类比成：HTTP 是 Web 的统一协议，MCP 是 LLM 工具调用的统一协议

1️⃣ 在没有 MCP 之前：

每个 Agent 框架自己定义 tool schema；

每个模型厂商定义自己的 function call 格式；

每个工具都要单独适配。

结果就是：强耦合 + 重复开发 + 不可迁移

MCP 提供：标准的工具描述方式，标准的请求响应格式，标准的能力暴露方式

2️⃣ 解耦模型和工具

传统 Function Call：模型直接输出 function name + args

MCP：模型只关心“我要用什么能力”，真正的工具调用由 MCP Client/Server 处理

架构变成：LLM ↔ MCP Client ↔ MCP Server ↔ Tool

好处：模型可以换，工具可以换，不需要重写代码

3️⃣ 支持远程工具（跨进程 / 跨机器）

Function Call 通常只能调用本地函数，写死在代码里

MCP可以连接远程，MCP Server可以跨语言，可以跨机器

比如：

GitHub MCP server

Notion MCP server

LeetCode MCP server

模型不需要知道它们怎么实现。

4️⃣ 支持动态能力发现

Function Call工具是提前注册好的

MCP支持 runtime discover tools

### 问题1.

> 【快手AI应用一面】 Transformer中的Q、K、V分别来自哪里？代表什么？

在 Transformer 中，Q、K、V 都来自同一个输入 embedding，通过**三组不同的线性变换矩阵**得到。

Attention 的核心是通过 Q 和 K 的点积计算相似度，再对 V 进行加权求和。

通过将匹配空间（Q、K）和信息空间（V）分离，模型获得了更强的表达能力。

在 **Self-Attention** 中 QKV 来自同一序列，在 **Cross-Attention** 中 Q 来自 **decoder**，K 和 V 来自 **encoder**。



### 引申问题

> QKV 矩阵计算，Transformer 底层原理，手撕一下

一、输入表示

输入序列：

$$
X \in \mathbb{R}^{n \times d}
$$

- $n$：序列长度
- $d$：embedding 维度

二、Q、K、V 的生成
$$
Q = XW_Q
$$

$$
K = XW_K
$$

$$
V = XW_V
$$

其中：

$$
W_Q, W_K, W_V \in \mathbb{R}^{d \times d_k}
$$

- **Q (Query)**：我需要什么？
- **K (Key)**：我能提供什么？
- **V (Value)**：真正传递的信息

三、Attention 计算过程

1️⃣ 相似度计算
$$
S = QK^T
$$

2️⃣ 缩放
$$
S' = \frac{QK^T}{\sqrt{d_k}}
$$

3️⃣ 归一化
$$
A = \text{softmax}(S')
$$

4️⃣ 加权求和
$$
\text{Output} = AV
$$

最终公式
$$
\text{Attention}(Q,K,V)
=
\text{softmax}\left(
\frac{QK^T}{\sqrt{d_k}}
\right)V
$$
四、Self-Attention
$$
Q = XW_Q
$$

$$
K = XW_K
$$

$$
V = XW_V
$$

Q、K、V 都来自同一个序列。

五、Cross-Attention
$$
Q = X_{\text{decoder}} W_Q
$$

$$
K = X_{\text{encoder}} W_K
$$

$$
V = X_{\text{encoder}} W_V
$$

六、多头注意力
$$
\text{head}_i
=
\text{Attention}(XW_Q^{(i)},XW_K^{(i)},XW_V^{(i)})
$$

$$
\text{MultiHead}(X)
=
\text{Concat}(\text{head}_1,...,\text{head}_h)W_O
$$

七、核心理解

- Q = 查询需求
- K = 特征标签
- V = 信息内容
- QK 决定“谁和谁相关”
- V 决定“传递什么信息”

实现：

$$
\text{匹配空间} \neq \text{信息空间}
$$
